# 002 – REST API and PostgreSQL persistence (contract-first, hexagonal)

## Intent
Turn the starter domain code into a running service, as the brief requires. It must:
- store time deposits and their withdrawals in PostgreSQL;
- expose **exactly two** REST endpoints, defined in a hand-written OpenAPI contract:
  - update the balances of all time deposits;
  - list all time deposits with their withdrawals;
- use a hexagonal architecture, so the interest logic stays framework-free and replaceable.

The calculator was just refactored behind 146 characterization tests (spec 001). This feature must reuse it as-is.

## Goals
- `openapi.yaml` is the source of truth. Server interfaces and DTOs are generated from it at build time, and the
  REST adapter implements the generated interface. Swagger UI serves that same file.
- Postgres schema managed by Flyway, with the two tables from the brief and seed data, so Swagger is useful immediately.
- Hexagonal layering:
  - the domain has no framework imports;
  - the application layer exposes input ports (use cases) and output ports (repository);
  - REST and JPA are adapters.
- Tests:
  - unit tests for the use cases;
  - Testcontainers Postgres for the persistence adapter and for end-to-end API tests.
- `docs/api.md` explains how to run the service and trigger both endpoints via Swagger.
- Each balance update also ages every deposit by one month (amendment, approved by the developer). See "Deposit ageing".

## Non-goals
- Input validation and error handling (out of scope per the brief).
- Creating, editing or deleting deposits or withdrawals. There is no third endpoint.
- Applying withdrawals to balances. Withdrawals are read-only history. Stored balances are taken as already net of
  withdrawals, and the calculator ignores withdrawals (design decision).
- Per-plan strategy refactor of the calculator (separate feature).
- Authentication, pagination, Actuator.

## Anti-goals (would be a failure even if it works)
- More than two API operations in the contract or the app.
- Any change to `TimeDeposit`'s constructor, getters or `setBalance`, or to `TimeDepositCalculator.updateBalance`'s
  signature or behaviour. All spec-001 tests must still pass unchanged.
- Spring, JPA or Jackson annotations on domain classes.
- Interest computed anywhere other than `TimeDepositCalculator`.

## Constraints
- Java 17 source/target (Spring Boot 4 minimum). Spring Boot **4.2.0** parent. springdoc-openapi **3.2.1**.
  openapi-generator-maven-plugin **7.27.0**. Flyway, Testcontainers, the PostgreSQL driver and Hibernate use the
  versions managed by Boot.
- Switching to the Boot parent replaces the old surefire 3.0.0-M3. JUnit and AssertJ versions become Boot-managed,
  and the existing tests must keep passing.
- `mvn verify` runs unit and integration tests. Integration tests need Docker.

## Approaches considered
| Approach | Trade-off | Decision |
|---|---|---|
| **A. Contract-first:** hand-written `openapi.yaml`, generated interface and DTOs, JPA + Flyway | One extra build plugin. The contract cannot drift and matches the brief's "OpenAPI Swagger contract". | **Chosen by the developer** |
| B. Code-first: hand-written controllers, springdoc generates the contract | Less tooling, but the contract is a by-product of the code | Rejected |
| Optimistic locking (`version` column) / no locking for concurrent updates | Extra column outside the brief's schema plus conflict handling / silent loss of a month's interest | Rejected; row lock chosen by the developer |
| Spring Data JDBC / `JdbcClient` instead of JPA | Less magic, but more mapping code | JPA chosen as the conventional option |

## API contract (summary of `openapi.yaml`)
- `GET /time-deposits`, operationId `getAllTimeDeposits`.
  - `200` returns an array of `TimeDeposit` (the order is ascending by `id`).
- `POST /time-deposits/balance-updates`, operationId `updateAllBalances`.
  - Applies one month of interest to every deposit in one transaction.
  - `204`, no body. Each call applies one more month and then adds 30 to every deposit's `days`; the endpoint is not
    idempotent by design.
- Schema `TimeDeposit`:
  - `id`: integer (int32)
  - `planType`: string
  - `balance`: number (decimal; generated as `BigDecimal`, two decimals)
  - `days`: integer (int32)
  - `withdrawals`: array of `Withdrawal`, empty when none
- Schema `Withdrawal`:
  - `id`: integer (int32)
  - `amount`: number (decimal)
  - `date`: string, format `date`
- All schema properties are required. `planType` is a plain string, not an enum, because unknown plan types already
  exist in the domain's behaviour and earn 0 interest.

## Database (Flyway `V1__create_tables.sql`, `V2__seed_data.sql`)
- `time_deposits`:
  - `id integer generated by default as identity primary key`
  - `plan_type varchar not null`
  - `days integer not null`
  - `balance numeric(19,2) not null`
- `withdrawals`:
  - `id integer generated by default as identity primary key`
  - `time_deposit_id integer not null references time_deposits(id)`
  - `amount numeric(19,2) not null`
  - `date date not null`
- **Assumption (document in the SQL comment):** the brief's `timeDeposits` and `timeDepositId` are written in
  snake_case. Postgres folds unquoted identifiers to lower case, so camelCase would need quoting everywhere.
- Seed data covers:
  - one deposit per plan;
  - an ineligible deposit (≤ 30 days);
  - a student deposit older than a year;
  - a premium deposit at 31–45 days;
  - deposits with zero, one and several withdrawals.

## Architecture
Follows the package structure in `CLAUDE.md` (decided by the developer). The domain classes already live in
`domain.model` / `domain.service`. All packages below are under `org.ikigaidigital`.

| Package | Contents |
|---|---|
| `domain.model` | existing `TimeDeposit` (gains an additive `setDays(int)`; constructor, getters and `setBalance` unchanged), `PlanType`; new framework-free records `Withdrawal` (`int id`, `BigDecimal amount`, `LocalDate date`) and `TimeDepositDetails` (`TimeDeposit deposit`, `List<Withdrawal> withdrawals`) |
| `domain.service` | existing `TimeDepositCalculator`, unchanged; `DepositAgeing` (`DAYS_PER_MONTH = 30`, `void advanceOneMonth(List<TimeDeposit>)`) |
| `business` | `TimeDepositService`: `List<TimeDepositDetails> getAll()` and `void updateAllBalances()`. `updateAllBalances` is `@Transactional` and does: load all with a row lock → `calculator.updateBalance(list)` → `depositAgeing.advanceOneMonth(list)` → `saveAll`. It only orchestrates; the rules live in `domain`. |
| `repository.api` | `TimeDepositRepository` port: `List<TimeDepositDetails> findAllWithWithdrawals()`, `List<TimeDeposit> findAllForUpdate()`, `void saveAll(List<TimeDeposit>)` (persists `balance` and `days`) |
| `repository.impl` | JPA entities `TimeDepositEntity` / `WithdrawalEntity`, Spring Data repositories, and `JpaTimeDepositRepository` implementing the port, including entity ↔ domain mapping |
| `rest.controller` | `TimeDepositController` implementing the generated API interface; generated interface `TimeDepositsApi` |
| `rest.dto` | generated API models (`TimeDepositDto`, `WithdrawalDto`) and the hand-written domain → DTO mapper |
| `application` | `TimeDepositApplication` (`@SpringBootApplication(scanBasePackages = "org.ikigaidigital")`) and `@Configuration` providing `@Bean TimeDepositCalculator` and `@Bean DepositAgeing`; JPA entity/repository scanning pointed at `repository.impl` |

- Generated code goes into `target/generated-sources`: apiPackage `org.ikigaidigital.rest.controller`, modelPackage
  `org.ikigaidigital.rest.dto`, model name suffix `Dto`.
  The generator (`spring` generator) runs with `interfaceOnly=true`, `useTags=true` and Jakarta EE / Spring Boot 4 compatible settings; the exact flags are an implementation detail.
- **Concurrent updates (developer's decision: row lock).** `findAllForUpdate` reads every deposit with
  `SELECT ... FOR UPDATE` (JPA `PESSIMISTIC_WRITE`) inside the `updateAllBalances` transaction. A second overlapping
  call waits for the first to commit, then applies its month on top. No schema change.
- **Money mapping:** the domain uses `Double`, the database and the API use `BigDecimal` with scale 2.
  - Entity → domain: `BigDecimal.doubleValue()`.
  - Domain → entity and API: `domain.model.Money.toCents(double)`, i.e. `BigDecimal.valueOf(double).setScale(2, HALF_UP)`,
    shared by both adapters so the API and the database cannot disagree.
  - This normalises accumulated `double` noise (e.g. `0.30000000000000004`) to cents at the boundary. The domain's
    in-memory behaviour is unchanged.
- **Reading withdrawals:** `findAllWithWithdrawals` loads deposits with their withdrawals in one query (fetch join or
  entity graph), ordered by deposit id and then withdrawal id. No N+1 queries.
- **Swagger:**
  - The contract file is also served statically at `/openapi.yaml`.
  - springdoc's generated docs are disabled (`springdoc.api-docs.enabled=false`), and Swagger UI is pointed at
    `/openapi.yaml`.
  - So Swagger shows the hand-written contract, and the API surface stays at exactly two operations.
- **Running locally:** `compose.yaml` with Postgres plus `spring-boot-docker-compose`, so `mvn spring-boot:run` starts
  the database automatically. Connection settings are in `application.yaml`.

## Deposit ageing (amendment)
Each `POST /time-deposits/balance-updates` represents one month passing.
- **Month length:** 30 days, following the standard 30/360 day-count convention. It matches the brief's "first 30 days"
  rule and keeps `days` an integer. Calendar months are not possible because the brief's tables store no dates for
  deposits.
- **Order:** interest is calculated with the current `days` first, then `days` increases by 30, in the same
  transaction. `days` therefore always means "age now", and the interest rules apply exactly to what `GET` shows.
  Example: a premium deposit at day 40 earns nothing on the first update and becomes day 70. It earns interest on the
  next update.
- **Where:** the domain service `DepositAgeing` holds `DAYS_PER_MONTH = 30`, with a comment citing the 30/360
  convention. `TimeDepositService` calls it after the calculator. `TimeDepositCalculator` is unchanged.
- Overflow of `days` near `Integer.MAX_VALUE` is out of scope (invalid input).

## Testing
- **Unit (`*Test`, surefire):** `TimeDepositService` with an in-memory fake `TimeDepositRepository` (no Mockito).
  - `updateAllBalances` saves exactly the balances the calculator produced, for all deposits.
  - `getAll` returns what the port returns.
- **Concurrency (`*IT`, Testcontainers):** two `updateAllBalances` calls run in parallel apply two months of
  interest. The final balances equal two sequential updates.
- **Persistence (`*IT`, failsafe, Testcontainers Postgres via `@ServiceConnection`):**
  - Flyway migrations apply.
  - `findAllWithWithdrawals` returns deposits ordered by id, each with its withdrawals.
  - `saveAll` persists two-decimal balances and the updated `days`.
- **End-to-end (`*IT`, `@SpringBootTest(RANDOM_PORT)` + Testcontainers):**
  - `GET` returns the seeded deposits matching the contract schema (all five fields, withdrawals nested).
  - `POST` returns 204, and a following `GET` shows the expected balances for the seed data (eligible deposits
    increased by hand-derived amounts, ineligible unchanged).
- The spec-001 tests stay unchanged and green.
- **Architecture (`ArchitectureTest`, plain JUnit):**
  - `domain` imports no framework and none of `business`, `repository`, `rest`, `application`;
  - `business` does not import `repository.impl` or `rest`;
  - `rest` does not import `repository`;
  - `repository.api` does not import `repository.impl`;
  - the test fails if the source directory is not found, instead of passing vacuously.

## Acceptance criteria
1. `openapi.yaml` defines exactly the two operations above, and the app exposes no other API operations.
2. `GET /time-deposits` returns every stored deposit with `id`, `planType`, `balance`, `days`, `withdrawals`.
3. `POST /time-deposits/balance-updates` updates and persists every balance using `TimeDepositCalculator`,
   atomically, and overlapping calls do not lose updates (row lock).
3a. The same call then adds 30 days to every deposit (30/360 convention), so repeated updates follow the plan rules
   as deposits age.
4. The schema matches the brief's tables (with the snake_case assumption), and it is created by Flyway with seed data.
5. Code follows the CLAUDE.md package structure: `domain` has no framework imports, and `rest` / `repository.impl`
   depend on `business` / `repository.api`, never the reverse.
6. `mvn verify` is green: the 146 spec-001 tests plus the new unit and integration tests.
7. `docs/api.md` describes how to start the app and call both endpoints via Swagger UI.
